# Флоу изменения: OpenSpec → Orca-ворктри → перекрёстное ревью

Копии навыка — `.claude/skills/feature-flow/` (Claude Code) и `.agents/skills/feature-flow/` (Codex); правятся вместе.

Общение с пользователем — по-русски, кратко; решения, которые меняют поведение для учащегося, принимает пользователь.
Коммиты и PR — без строк о соавторстве Claude. Комментарии в коде — только неочевидное «почему».

## 1. Обсуждение
- Разобрать запрос по коду и данным курса (цифры, а не впечатления), предложить 2–3 варианта с рекомендацией.
- Решение пользователя записать дословно с датой — оно пойдёт в proposal.

## 2. План: OpenSpec в Orca-ворктри
- Ворктри: `orca worktree create --name <change> --no-parent --setup run --json` (база — свежий `main`).
- Изменение по навыку `.agents/skills/openspec-propose/SKILL.md`: `openspec new change <name>`, артефакты proposal, design, specs, tasks по `openspec instructions <artifact> --change <name> --json`. Артефакты по-русски, SHALL/MUST по-английски; в proposal требование пользователя отделено от предлагаемого объёма; у каждой задачи — проверка.
- Зависимость между изменениями и порядок архивации — первой строкой в tasks.md; MODIFIED-требования — полным текстом поверх того изменения, что архивируется раньше.
- `openspec validate <name> --strict` и `prettier --check openspec/changes/<name>`.
- Статус ворктри: `orca worktree set --worktree path:<path> --comment "…" --json`.

## 3. Перекрёстное ревью плана
- Независимый ревьюер — субагент или отдельная сессия агента (например, `orca worktree create --agent codex`), строго только чтение, временные файлы — вне репозитория. Задача: сверить каждое утверждение плана с кодом (file:line), найти пробелы, противоречия между артефактами, пересечения с соседними изменениями, нарушения PRODUCT.md. Вывод: Blocking / Serious / Minor со сценарием отказа и исправлением.
- Самые неожиданные находки проверить самому. Спорные решения вынести пользователю, остальное исправить; повторить ревью, если правки крупные.
- План можно смержить в `main` отдельным PR (только `openspec/changes/<name>`) — тоже только с разрешения пользователя.

## 4. Реализация
- Свежий ворктри от `main`; если `main` ушёл вперёд — `git rebase origin/main` до начала.
- Базовый прогон тестов до правок. Задачи — по порядку tasks.md, тест на каждую; отклонения от дизайна записать в раздел «Реализация» в design.md; отметить `- [x]`.
- Полная проверка — набор CI (`.github/workflows/ci.yml`); `npm test` заменяет `test:unit` и `test:heavy`:
  ```
  npm run format:check && npm run lint && npm run typecheck && npm run check:config && npm run spec && npm run lexicon:check && npm test
  BASE_PATH=/ VITE_TELEGRAM_MOCK= VITE_TELEGRAM_BOT=TetradioBot SENTRY_DEBUG_IDS=1 VITE_SENTRY_DSN=https://00000000000000000000000000000000@o0000000.ingest.de.sentry.io/0000000000000000 npm run build
  BASE_PATH=/ npm run check:bundle
  VITE_TELEGRAM_MOCK=1 npm run build && npm run lighthouse
  npm run test:e2e && npm run test:e2e:course && npm run test:e2e:courses
  ```
- Экраны — проверить скриншотом временного e2e-теста, затем удалить его.

## 5. Перекрёстное ревью кода
- Два независимых ревьюера параллельно, по областям (например: домен, хранилище, синхронизация — и интерфейс, тексты, тесты), только чтение, по незакоммиченному diff.
- Блокирующее проверить тестом, который падает без исправления и проходит с ним. Исправить, снова полная проверка.

## 6. PR и мерж
- Коммит, `git push`, `gh pr create` с описанием: что сделано, проверки, что осталось (обычно — проверка на устройстве).
- Мерж — только по явному разрешению пользователя на этот PR. Разрешение из прошлой задачи или прошлого PR не переносится. В фоне `gh pr checks <n> --watch`, затем сообщить итог CI и ждать ответа. По разрешению и при всех `pass` — `gh pr merge <n> --squash`.
- После мержа: `git pull --ff-only` в основном репозитории, статус ворктри `completed`; смерженные ворктри удалить `orca worktree rm` после проверки, что в них нет изменений.
- Предупредить пользователя о выпуске, если меняется формат облака или база: копия данных и обновление всех устройств.
