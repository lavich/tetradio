## Context

Синхронизация (`src/sync/`): ключи облака `p_<устройство>`, `v_<версия>_<n>`, `cp_<устройство>` (`adapter.ts:72-78`); транспорт `removeItems` режет вызовы по 64 (`transport.ts:154-157`), тайм-аут 15 с; удаления «всего» нет. Координатор (`coordinator.ts`): `start()` :712, `stop()` :758 не ждёт идущего обмена; блокировка `webLock(tetradio-sync-<база>)` берётся с `ifAvailable` и при занятости обмен пропускается (:767-779); отсутствие своего указателя при живых локальных данных ведёт к повторной публикации (:388-399). База — `db` (`src/storage/db.ts:115`), имя `tetradio-tg-<бот>-<id>` (`profile.ts:50`); переоткрытие при сбое — `reopenDatabase` (`recovery.ts:36-39`), его зовут `storageHealer`, лечение синхронизации и `Recovery.tsx`. Очередь отчётов удаляет `setReportingEnabled(false)` (`reporting.ts:139-158`). Хранилища браузера — таблица ключей ниже. Диалог по образцу «Заменить данные копией» (`BackupSection.tsx:148-176`, `AlertDialog`, `variant="destructive"`). После восстановления копии приложение не перезагружается — для удаления нужна своя перезагрузка. Worker: `/feedback` с проверкой `initData` (`bot/worker.ts:82-108`, `bot/form.ts`), Bot API через `call` (`bot/feedback.ts:84-95`), хранилище без удаления (`bot/store.ts`).

## Goals / Non-Goals

**Goals:** удаление одним действием без возврата данных синхронизацией; ничего локального не удаляется, пока не удалено облако (и переписка, если выбрана); тесты на порядок шагов и сбои; e2e на эмуляторе Telegram.

**Non-Goals:** удалённое удаление на других устройствах; отчёты Sentry; файлы копий.

## Decisions

**Порядок.**

1. Переписка (если галочка): `POST /forget` к Worker — до любых локальных шагов: нужен `initData`, а сбой не должен оставить человека без данных на устройстве.
2. Модуль синхронизации загружается, если ещё не загружен (`loadSync`), — иначе догрузившись позже, `connectSync` запустил бы обмен. Затем `sync.halt(work)`: флаг остановки (`exchange`, `start`, повтор из `fail`, `again` ничего не запускают; `resolve` проверяет флаг после ожидания идущего обмена), снятие листенеров, ожидание идущего обмена и затем `navigator.locks.request` той же блокировки с `AbortSignal.timeout(20000)`; `work` выполняется внутри, блокировка держится до конца удаления базы. Без Web Locks — флаг и ожидание обмена. Тайм-аут — «Синхронизацией занята другая вкладка — закройте её и повторите.» Сбой до конца облачного шага — `sync.resume()` (снимает флаг, `start()`, если координатор был запущен), отметка снимается.
3. Внутри: отметка `tetradio:erasing:<имя базы>` = `cloud` в `localStorage`; `cycleOnce` и `resolve` любой вкладки перед публикацией проверяют отметку и не публикуют (защита для вкладок без Web Locks и не остановленных).
4. Облако: решается по профилю — в Telegram нужен мост с CloudStorage по той же проверке, что `capabilities.cloudStorage` (`platform/adapter.ts:124`: `getItems` и Bot API 6.9), и владелец моста должен совпадать с профилем (`ownerMatches`); транспорт создаётся из моста, если адаптер ещё выключен. Без облака — «Облако Telegram недоступно — перезапустите приложение и повторите.», ничего не удаляется. Удаляются все ключи CloudStorage бота (область только этого Mini App) в порядке `p_` → `cp_` → `v_` → прочие. `SyncError("unavailable")` — тот же текст; прочие сбои — «Не удалось удалить данные из облака Telegram. Проверьте сеть и попробуйте ещё раз.»; если переписка была удалена — с «Переписка уже удалена.». Вне Telegram облачного шага нет.
5. Отметка = `local`. Корень React заменяется статичным «Удаляем данные…» через `showStatic()` из `src/app/root.ts` (туда выносится `createRoot` из `main.tsx`): нет живых запросов, эффектов и границы `Recovery`, которая через `reopenDatabase` пересоздала бы базу.
6. Отчёты: `setReportingEnabled(false)` (без DSN — только состояние `off`), затем `clearReportQueue()` — ожидаемое `indexedDB.deleteDatabase("tetradio-error-reports")` с `onsuccess`/`onblocked` и тайм-аутом 5 с.
7. `db.close({ disableAutoOpen: true })`, `Dexie.delete` базы приложения и `tetradio-restore` с тайм-аутом 10 с на `blocked`. Сбой шагов 6–7 — отметка остаётся, статичный экран: «Закройте другие окна приложения и перезапустите — удаление завершится при запуске.»
8. Хранилища браузера: `localStorage` — `tetradio:haptics:<имя базы>` этого профиля и общие `tetradio:feedback-draft`, `word-taps-hint`, затем отметка; `sessionStorage` — `scroll:*`, `tetradio:sw-dropped`. Остаются: `tetradio:launch` и `__telegram__*` (параметры моста: без них после перезагрузки у моста пустой `initData` и версия 6.0), `tetradio:start-consumed`, служебные `tetradio:auto-update-build`, `tetradio:stale-build-reload`, `tetradio:start-skip-reload`.
9. `skipStartRouteOnReload()` (без `query_id` ссылка запуска `w_`/`c_` иначе открылась бы снова), `location.replace(${BASE_URL}app/)` — старт как у нового пользователя; настройки по умолчанию, отчёты снова включены (сказано в диалоге).

**Отметка при запуске.** `main.tsx`, в `start()` до `db.open()`, `refreshCatalog()`/`syncCourses()`, `deferredLoad(loadSync)` и `launchSync`: при отметке `Recovery`/`App` не рендерятся, синхронизация не подключается, показывается статичный экран «Завершаем удаление данных…». Фаза `local` — шаги 6–9 без моста и сети. Фаза `cloud` — `initPlatform`, ожидание моста, шаг 4 с транспортом из моста, затем шаги 6–9; при отказе — тот же экран с «Повторить» и «Отменить удаление» (снимает отметку и перезапускает: облако может быть очищено частично, обычный запуск опубликует данные устройства заново — человек отменил удаление сам).

Альтернатива — сначала база, потом облако: при сбое облака человек остался бы без локальных данных, а облако вернуло бы их.

**Worker `/forget`.** Свой разбор тела (одно поле `initData`, до 16 КБ), `Origin` из `APP_ORIGINS`, CORS, `verifyInitData`. Адрес — `new URL("forget", VITE_FEEDBACK_URL)`. Строка пользователя → если есть тема — `deleteForumTopic` (ответы `TOPIC_ID_INVALID` и «thread not found» — успех: тема уже удалена; проверено на Bot API 26.10.2026); затем `forgetUser`: заблокированный — обнуляются все поля, кроме `blocked` (законный интерес: защита от злоупотреблений; так в политике); иначе строка удаляется. Ответы: 200, 400 `invalid`, 401 `stale`, 502 `failed`, 503 без настройки. Частоту не ограничиваем: действие идемпотентно. Право бота «Удаление сообщений» есть (проверено `getChatMember` 26.10.2026).

**Разблокировка без темы.** После `/forget` у заблокированного нет темы. В общей теме группы поддержки (`!is_topic_message`, проверка до ветки темы в `fromAuthor`; только люди или анонимный администратор группы): `/blocked` — список id с отметкой блокировки без темы; `/unblock <id>` (только цифры) — снимает отметку и удаляет пустую строку; id без отметки блокировки — «Нет заблокированного пользователя с таким id.».

**Интерфейс.** `src/features/backup/DeleteData.tsx`: раздел и диалог (`AlertDialog`), нативный `input type="checkbox"` с подписью «И переписку с автором» при `formAvailable()`; «Сначала сохранить копию» — общий хук сохранения копии (вынести из `BackupSection`), результат передачи файла — в диалоге; «Удалить» — `variant="destructive"`, недоступна во время сохранения копии; во время удаления диалог не закрывается (`onOpenChange` игнорируется). Перечень удаляемого: прогресс, слова, ответы и настройки на устройстве; снимок и отложенные версии в облаке Telegram (отложенных версий нет в полной копии); при галочке — тема в группе поддержки. Предупреждения: другие устройства; отчёты об ошибках снова включатся; копии сообщений в личном чате с ботом удаляете вы сами. Тексты ошибок: переписка — «Не удалось удалить переписку. Попробуйте позже.» (401 — «Перезапустите приложение и повторите.»); облако — с уточнением «Переписка уже удалена.», если она была удалена.

**Политика.** «Сроки» и «Ваши права» (RU и EN): устройство и облако — кнопка «Удалить мои данные» в «Настройках и данных», повторить на каждом устройстве; переписка — галочка там же или запрос через «Написать автору»; копии сообщений в чате с ботом удаляет сам человек; отчёты Sentry кнопкой не удаляются (по идентификатору через автора); у заблокированного хранятся id и отметка блокировки (законный интерес, ст. 6(1)(f)). Дата редакции.

## Risks / Trade-offs

- [Второе устройство возвращает данные] → предупреждение в диалоге; удалённого удаления нет.
- [Удаление прервано после облака] → отметка `tetradio:erasing` доводит удаление при следующем запуске без синхронизации.
- [Соседняя вкладка держит блокировку] → тайм-аут 20 с и текст про другую вкладку.
- [Бот без права удалять сообщения] → `/forget` отвечает ошибкой, приложение пишет «Не удалось удалить переписку», локальное не трогает; проверка права до мержа.
- [Человек удалил данные случайно] → диалог, «Сначала сохранить копию», восстановление из копии.

## Реализация

- Удаление ключей облака — функция `removeAllKeys(transport)` в `src/sync/adapter.ts`, не метод `SyncAdapter`: интерфейс и тестовые адаптеры не меняются, транспорт для удаления создаётся из моста.
- `SyncCoordinator`: `halted` и `started`, `halt(work)`, `resume()`, опция `exclusive` (в приложении — `webLockWait`, 20 с, `LockTimeout`); `exchange`, `start`, повтор из `fail` при остановке ничего не запускают; `resolve` проверяет остановку и отметку после ожидания идущего обмена; `cycleOnce` при отметке `tetradio:erasing:<база>` — `paused` «Идёт удаление данных.» без публикации.
- `src/storage/erase.ts` — `eraseMyData`, `finishLocal`, `resumeErase` с зависимостями (`EraseDeps`), сборка зависимостей — `src/app/erase-deps.tsx`; `src/storage/erase-marker.ts` — отметка; `src/storage/delete-database.ts` — удаление IndexedDB с тайм-аутом; `clearReportQueue` в `reporting.ts`; корень React — `src/app/root.tsx` (`appRoot`, `showStatic`), экран — `ErasingScreen.tsx`. `main.tsx` при отметке динамически импортирует модули удаления — стартовый граф без кода синхронизации.
- Запросы к боту из приложения — общий `postToBot` в `src/platform/feedback-send.ts`; `forgetMessages` берёт адрес `forget` рядом с `VITE_FEEDBACK_URL`.
- Worker: общий `appRoute` для `/feedback` и `/forget` (CORS, тело, подпись); `readInitData` в `bot/form.ts`; `forget` и команды общей темы в `bot/feedback.ts`; `forgetUser`, `blockedWithoutTopic`, `unblock` в `bot/store.ts`; `Database.all` для списка.
- Диалог: нижние кнопки в мобильной раскладке идут снизу вверх («Удалить» сверху) — так устроен `AlertDialogFooter`; скриншоты 390 px — раздел и диалог.
- `privacy-page` архивирован в этом изменении.
- После ревью кода: SDK отчётов никогда не закрывает свою базу IndexedDB (`tetradio-error-reports`), поэтому в той же вкладке её удаление упиралось в `blocked` и удаление каждый раз заканчивалось экраном «Закройте другие окна». Устройство теперь очищается при следующем запуске (`resumeErase`, фаза `local`): в сессии — только переписка, облако, отметка `local` и перезапуск (тест `tests/erase.test.ts` «SDK держит свою базу открытой» падал до исправления). Шаги «статичный экран перед закрытием базы» и замена корня в сессии больше не нужны — живые запросы закрывает перезапуск.
- Облако проверяется до удаления переписки (иначе отказ «облако недоступно» оставлял бы переписку удалённой); владелец моста — строгое равенство с `profile.userId`; сбой загрузки синхронизации — `EraseFailure("cloud", withMessages)`; `deleteDatabase` при `onerror` отклоняется (отметка остаётся); `webLockWait` без `AbortSignal.timeout` (Safari 15.4–15.x); `start()` во время остановки запоминается для `resume`; код удаления в «Настройках» грузится по нажатию — чанк настроек без кода синхронизации; при сбое загрузки модулей доведения — текст вместо перезагрузок.
- Автообновление между `/forget` и отметкой может перезагрузить страницу — переписка удалена, остальное нет, без сообщения; риск низкий. Вторая вкладка Telegram Web после `versionchange` пересоздаёт пустую базу и после снятия отметки публикует пустое состояние — личные данные так не возвращаются.
- Модуль удаления берёт `removeAllKeys`, `LockTimeout`, `cloudStorageTransport` и `SyncError` из `src/sync/index.ts`: прямые импорты из `coordinator.ts` и `transport.ts` выносили координатор в отдельный чанк, и ленивые чанки первого экрана превышали бюджет Lighthouse (36 198 > 36 000 байт); после — 35 456.
- Полный набор CI зелёный; нестабильный `tests/hidden-course-screens.test.tsx` (из #287) в одном из прогонов падал по времени — отдельная задача.
