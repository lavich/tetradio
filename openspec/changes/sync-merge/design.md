## Контекст

- Снимок (`CompactSnapshot`, `src/sync/types.ts:56`): `lessons`, `packages`, `blocks`, `states` (FSRS; включая карточки из `cardStash` и незнакомых видов), `skills` (по карточке: по типам `recent[]` + `lastAt`, `lastTypes`, `cleanAssemblies`), `stats` (`days[]` с числом ответов и ключами, `recentByType`, `answers`, `answeredKeys`), `reviewDays`. Истории ответов в облаке нет — пересчитать FSRS по объединённой истории нельзя.
- Решение координатора (`src/sync/coordinator.ts:520-560`): без отметки и при одной версии-кандидате новее — применить; иначе конфликт `diverged` / `remote` / `initial` / `restored`. Выбор версии публикует её с часами, покрывающими ветви (`resolves`).
- Предка как снимка сейчас нет: `meta` хранит `sync:applied` (id) и `sync:clock`; `baseSummary` — только статистику, дни и отсечку; версии облака предыдущих поколений удаляет уборка (`cleanup`, `coordinator.ts:733`).
- `syncVersions` (локальная таблица, не входит в копию — `backup.ts:36`) хранит конфликтные и отвергнутые версии; её id защищают свои поколения в облаке от уборки (`coordinator.ts:744`).
- Дни повторений уже складываются при любом выборе (`docs/sync.md`, «Дни повторений»); паузы курсов — отдельный ключ со слиянием по времени.

## Решения

### 1. Общий предок

Предок — снимок последней версии, синхронизированной на этом устройстве: применённой (`applySnapshot`) или опубликованной (`publish`, включая выбор версии и результат слияния). Пишется в той же транзакции, что `sync:applied`/`sync:clock`, строкой `syncVersions` с фиксированным id `base` и ролью `base` (тип `SyncVersionRow.role` расширяется; схема Dexie не меняется). Фиксированный id не совпадает с id поколения, поэтому не защищает облачные части от уборки (`coordinator.ts:744`); «Отложенные версии облака» показывают только роли `rejected`/`conflict`.

Объём — один снимок (как одна версия облака: десятки–сотни КБ JSON); хранится несжатым объектом, как остальные строки таблицы.

Предок пригоден для ветви облака, если её часы покрывают часы предка (`dominates(branch.clock, base.clock)`) — ветвь происходит от него. Предок пропадает: восстановление копии (`restoreBackup` удаляет строку вместе с `sync:publishing`/`sync:later`), удаление данных; его нет до первого обмена после обновления.

Варианты: (а) строка `syncVersions` — выбрано: без новой таблицы и миграции, вне копии; (б) ключ `meta` — `meta` входит в копию за вычетом префикса `sync:`, строка в сотни КБ мешает копии и чтению `meta`; (в) брать предка из облака (свой указатель) — не работает после применения чужой версии: её прежнее поколение убрано уборкой.

### 2. Правила слияния (`src/sync/merge.ts`, чистая функция)

`merge(base, branches[])` → снимок. Для каждого поля: «изменилось на стороне» = отличается от предка. Если изменила одна сторона — берётся её значение; если несколько — правило поля. Все правила симметричны (не зависят от порядка ветвей; равенство разбивается по id ветви), поэтому одновременное слияние на двух устройствах даёт одинаковое содержание.

| Поле | Изменила одна сторона | Изменили обе |
| --- | --- | --- |
| `states[ref]` (FSRS, в т. ч. `cardStash`, незнакомые виды) | её состояние | **открытый вопрос 1**; рекомендация — состояние с более поздним `card.last_review`; `version` = max + 1; `introducedAt` = min |
| `states`: карточка есть у предка, нет у стороны | убрать, если другая сторона её не меняла | оставить изменённую |
| `lessons[id]` | её | `completed` = или; `updatedAt` = max |
| `blocks[lesson, block]` | её | `done` = или; `score`/`checks` — у более позднего `updatedAt`; `updatedAt` = max |
| `packages` | объединение | объединение |
| `skills[ref].types[type]` | её | у более позднего `lastAt` (последние 10 исходов этого типа — одной стороны) |
| `skills[ref].cleanAssemblies` | её | `L + R − A` |
| `skills[ref].lastTypes` | её | у стороны с более поздним `lastAt` по карточке |
| `stats.days[date]` | её | `answers` = `L + R − A` (по дате, неотрицательно), `keys` = объединение; окно `KEEP_DAYS` |
| `stats.answers` | её | `L + R − A` |
| `stats.answeredKeys` | объединение | объединение |
| `stats.recentByType[type]` | её | у стороны с более поздним ответом этого типа (по `skills.lastAt`) — точное слияние скользящего окна невозможно |
| `reviewDays` | объединение (как сейчас) | объединение |

Незнакомые поля и типы формата 5 переносятся как непрозрачные значения по ключу `ref`/типа.

### 3. Где в координаторе

В `decide` вместо конфликта `diverged`/`remote`: если предок есть и все ветви облака происходят от него — `merge(base, [local, ...remote])`, применение результата одной транзакцией поверх локальной базы (отметка изменений должна совпасть с прочитанной при сборке локального снимка, иначе — решать заново, как `ifClean`), затем публикация с часами `max(все ветви) + свой счётчик` и `resolves` = id ветвей облака. Публикация идёт обычным путём `sync-reliability` (начатая публикация, `sync:issued`). Новый предок — опубликованный результат.

Три устройства и `remote`: если все ветви происходят от предка — сливаются вместе (правила n-арные); иначе — окно, как сейчас (**открытый вопрос 3**).

Одновременное слияние на двух устройствах: результаты совпадают по содержанию, но часы разные и не покрывают друг друга. Следующий обмен видит чужой результат как расхождение; предок (свой результат) — его содержание совпадает с чужим, проверка «ничего не опубликовано» (`sync-reliability`) сравнивает содержание и применяет чужую версию без окна. Тест обязателен.

### 4. Формат облака

Не меняется. Результат слияния — обычный снимок; `resolves` уже есть. Прежние версии приложения применяют его как версию, покрывающую их собственную; сами они продолжают показывать окно (поведение прежней версии). `sync-format-compat` должен проходить без изменений.

### 5. Что видит учащийся

Окно остаётся для `initial`, `restored`, ветвей не от предка и ошибок слияния (исключение в `merge` — конфликт, как раньше, с отчётом об ошибке). После слияния — **открытый вопрос 2**.

## Риски

- **Одна карточка, отвеченная на обоих устройствах**: при правиле «позже побеждает» влияние ответа другой стороны на интервал теряется (ответ остаётся в навыках и статистике). Учащийся может увидеть карточку раньше или позже, чем при последовательных ответах. Частота — только у карточек, повторённых на обоих устройствах в одном окне офлайн.
- **Агрегаты статистики**: `L + R − A` точен для счётчиков; скользящие окна (`recentByType`, `recent[]` навыка) — приближение.
- **Предок устаревает**, если устройство долго не синхронизировалось, а другие несколько раз выбирали версии окном: ветви не происходят от предка → окно, как раньше.
- **Объём**: ещё один снимок в IndexedDB на устройстве.

## Открытые вопросы

1. **Одна карточка изменена на обоих устройствах.** Варианты: (а) состояние с более поздним ответом (рекомендация: просто, предсказуемо; теряется влияние одного ответа на интервал); (б) состояние с меньшей стабильностью — карточка вернётся раньше (осторожнее для памяти, но может вернуть уже хорошо выученную); (в) окно выбора только для таких карточек — сложно объяснить. Рекомендация — (а).
2. **Уведомление о слиянии.** (а) тихо, только статус «Синхронизировано» (рекомендация: учащемуся нечего делать); (б) один раз тихая строка «Объединены занятия с <устройство>» на «Прогрессе»; (в) сохранять локальный снимок до слияния в «Отложенных версиях облака» на 30 дней как страховку (рекомендация — да, вместе с (а): ничего не показывает, но даёт откатиться).
3. **Конфликт `remote` (две версии других устройств).** (а) сливать, если обе происходят от предка этого устройства (рекомендация); (б) оставить окно.
