## Context

`bot/worker.ts` (архив `2026-10-26-bot-start`) отвечает на вебхук одним вызовом в теле ответа и не хранит токен бота; на любое сообщение, кроме `/start`, — «Сообщения боту пока не читаются». Выкатка — job `worker` в `deploy.yml` после зелёного CI на `main`, окружение `cloudflare`; вебхук зарегистрирован с `allowed_updates: ["message"]` и параллельной доставкой по умолчанию (`scripts/bot-webhook.ts`). В приложении экран сбоя получает `reportId` — 32 шестнадцатеричных символа или `null`, если отчёты выключены (`src/app/CrashScreen.tsx:27-33`, `src/main.tsx:106-117`, `src/app/Recovery.tsx:39`, `src/reporting/reporting.ts:65-67`); имя бота запуска — `launchContext().bot`, синхронно из адреса, доступно и на экране отказа базы (`src/platform/launch.ts:17-18`, `:58`); ссылки Telegram открываются через `openTelegramLink` (как в `src/platform/share.ts`). Проект Sentry — `storewizard/tetradio`.

## Goals / Non-Goals

**Goals:**

- Переписка пользователя с автором через бота: тема на пользователя, ответы из темы.
- Без текстов сообщений в хранилищах вне Telegram; без личного аккаунта автора в переписке.
- Логика Worker проверяется unit-тестами без сети: Bot API и хранилище подменяются.

**Non-Goals:**

- Правки сообщений: `edited_message` не входит в `allowed_updates`, правка не доходит ни в тему, ни пользователю.
- Связь «ответ автора → сообщение пользователя»: у пользователя копия без цитаты.
- Обратная связь в боте разработки (`?bot=`): у него нет Worker.

## Decisions

**Последовательная доставка.** Telegram по умолчанию держит до 40 одновременных запросов к вебхуку, а альбом — это несколько отдельных `message`. Параллельные обработчики нового пользователя прочитали бы пустую связь и создали несколько тем. `scripts/bot-webhook.ts` регистрирует вебхук с `max_connections: 1`: следующее обновление приходит после ответа на предыдущее. Обработка синхронная, без `ctx.waitUntil` — иначе ответ уходит раньше и последовательность теряется. Альтернатива — Durable Object как замок: ещё один вид хранилища ради того, что даёт один параметр.

**Ответ пользователю — в теле ответа на вебхук.** Всё, что получает сам пользователь, — один вызов в теле ответа, без токена: приветствие и приглашение на `/start`, текстовое подтверждение или реакция 👍 (`setMessageReaction`), текст о сбое. Токен нужен только для работы с группой. Поэтому неверный или отозванный `BOT_TOKEN` не делает бота немым: первый же отказ Bot API (в том числе 401/404) превращается в «Не удалось передать сообщение» в теле ответа.

**Запасной режим.** Если нет `BOT_TOKEN`, `SUPPORT_CHAT_ID` или привязки `FEEDBACK`, бот отвечает как `bot-start`: на любой `/start`, включая `feedback` и `fb_<id>`, — приветствие, на прочее — «пока не читаются». Выкатка раньше настройки не обещает пользователю пересылку, которой нет.

**Вызовы Bot API с токеном.** Работа с группой требует нескольких вызовов (тема, шапка, ссылка на отчёт, копия) — через `fetch` к `api.telegram.org` с секретом Worker `BOT_TOKEN`. Ответ 429 с `retry_after` до 5 секунд — одно ожидание и повтор; дольше — сбой пересылки. Предел частоты в одну группу — около 20 сообщений в минуту: новый пользователь — 3–4 сообщения, альбом из 10 фото — 10. Весь `handle` — в `try`: после обработки, в том числе при исключении, ответ 200 без тела, иначе Telegram повторит доставку и продублирует сообщение в теме.

**Группа поддержки — супергруппа с темами.** Бот — администратор с правом «Управление темами»: администратор получает все сообщения группы. `SUPPORT_CHAT_ID` — переменная в `wrangler.jsonc` (строка; сравнивается с `String(chat.id)`). Из группы принимаются только сообщения с `is_topic_message: true` и `message_thread_id`, связанным с пользователем. Отправитель — человек (`from.is_bot` ложно) или анонимный администратор (`sender_chat.id` равен группе поддержки); прочие боты, общая тема и служебные сообщения (`forum_topic_*`, `new_chat_members`, `left_chat_member`, `pinned_message` и подобные) пропускаются. Сообщения других групп и каналов — без ответа.

**Пересылка — `copyMessage`, не `forwardMessage`.** Копия не показывает отправителя: в теме не видно скрытого пересылкой аккаунта, у пользователя — аккаунта автора. Служебные сообщения, платные медиа, розыгрыши и счета не копируются — `ok: false`, это сбой пересылки.

**Порядок шагов пересылки.** Чтение строки пользователя → при необходимости `createForumTopic` и запись строки (тема и пользователь одной записью) → шапка → ссылка на отчёт → `copyMessage` → запись `ack_at`, если подтверждение текстовое, и снятие `fb` → ответ пользователю в теле. Сбой на любом шаге до копии — «Не удалось передать», `ack_at` не меняется; тема, созданная до сбоя, остаётся связанной с пользователем, и следующее сообщение пойдёт в неё.

**Тема пользователя.** При первом сообщении — `createForumTopic` с именем `<имя> <фамилия> (@username)` без отсутствующих частей, обрезанным до 128 символов; затем в тему шапка без разметки: имя, @username или «без username», id, `language_code`. Если `copyMessage` в тему отвечает `message thread not found` (тему удалили) — новая тема, перезапись строки и один повтор.

**D1 — связи без текстов.** Связь «пользователь ↔ тема» должна читаться сразу после записи: альбом — несколько обновлений подряд, и второе обязано увидеть тему первого. Cloudflare KV этого не гарантирует (отрицательный ответ кэшируется на узле до минуты) и на бесплатном плане даёт 1000 записей в сутки и одну запись в секунду в ключ; D1 (SQLite) строго согласован и даёт 100 000 записей в сутки. Одна таблица `users`: `user_id` (первичный ключ), `thread` (уникальный), `ack_at`, `blocked`, `fb`, `fb_at`. Тема и пользователь — одна строка, поэтому связь в обе стороны пишется атомарно. `fb` — id отчёта из `/start fb_<id>`, действителен сутки (`fb_at`), стирается после того, как ссылка ушла в тему. Схема — миграция `bot/migrations/0001_users.sql`, применяется `wrangler d1 migrations apply --remote` до выкатки кода. В D1 — id пользователей и тем, время подтверждения, отметка блокировки и id отчёта Sentry; текстов нет. Альтернатива — KV с повтором чтения: не убирает гонку, только сужает её.

**Команды в теме.** Перед разбором от команды отрезается `@<бот>`. `/block` — `blocked: true`, в теме «Заблокирован: сообщения пользователя не пересылаются. /unblock — вернуть.»; `/unblock` — снимает. Прочие сообщения, начинающиеся с `/`, не пересылаются: в теме — «Команда не отправлена пользователю. /block, /unblock — блокировка.» Ответ автора копируется без подписи; отказ Telegram — «Не доставлено: <описание Telegram>» в теме.

**Ссылка на отчёт.** `Отчёт: <SENTRY_EVENT_URL><id>/` перед копией первого сообщения после `/start fb_<id>`. Формат адреса события проверяется на живом отчёте при настройке (задача 1.3). Идентификатор создаётся в приложении, поэтому событие могло не дойти до Sentry — тогда ссылка ведёт на «не найдено», это допустимо.

**Структура Worker.** `bot/worker.ts` — `fetch`: метод, секрет, разбор JSON, запасной режим, сборка зависимостей из `env`; `bot/feedback.ts` — чистая логика `handle(update, deps)`, где `deps` — `api(method, body)`, хранилище связей (`byUser`, `byThread`, `save`), конфигурация, `now()` и `sleep(ms)`; результат — вызов для тела ответа или `null`; `bot/store.ts` — хранилище на D1; `bot/texts.ts` — тексты. Тесты подменяют `api` записью вызовов и хранилище — словарём; запросы `bot/store.ts` проверяются на `node:sqlite` той же миграцией. Только Web API; тела обновлений и тексты не логируются.

**Приложение.** Ссылка и её открытие — отдельный модуль `src/platform/feedback.ts`: экран сбоя входит в стартовый чанк, а `share.ts` тянет `sonner`, который приложение грузит лениво (+34 КБ к стартовому графу). Бот ссылки — `launchContext().bot` в Telegram и `CONFIGURED_BOT` вне его (`src/platform/launch.ts:31-32`): иначе `?bot=` в адресе уводил бы сообщение и id отчёта в чужого бота; без `CONFIGURED_BOT` вне Telegram кнопки нет. `feedbackLink(bot, reportId)`: `https://t.me/<bot>?start=fb_<id>`, если `reportId` — 32 шестнадцатеричных символа, иначе `?start=feedback`. Открытие — `openTelegramLink`, если мост Telegram доступен; иначе `window.open(url, "_blank", "noopener")` — в WebView Telegram ссылка `t.me` тоже открывает чат. Раздел «Обратная связь» (`id="feedback"`) в `SettingsScreen.tsx` после «Отчётов об ошибках»; на экране сбоя кнопка «Написать автору» после «Скопировать диагностику» и её статуса. Экран сбоя не открывает базу; ссылка собирается при нажатии — `reportId` приходит на экран чуть позже его появления (`CrashScreen.tsx:36`).

## Risks / Trade-offs

- [Токен бота в секретах Cloudflare] → утечка Worker-а или токена Cloudflare даёт полный доступ к боту. Меры: токен Cloudflare только в окружении `cloudflare`; при подозрении — `/revoke` в BotFather, новый `BOT_TOKEN` и перерегистрация вебхука.
- [Последовательная доставка] → медленный ответ Bot API задерживает следующие обновления; при потоке больше одного сообщения в секунду очередь растёт. Для обратной связи одного автора это приемлемо.
- [Тайм-аут обработки] → Telegram повторит обновление, сообщение может прийти в тему дважды; если обработка прервалась между созданием темы и записью строки, повтор создаст вторую тему.
- [Предел частоты в группу] → альбомы двух новых пользователей подряд упираются в 429 с ожиданием больше 5 секунд; часть фото получает «Не удалось передать» — пользователь видит это и отправляет снова.
- [Любой участник группы отвечает от имени бота] → группа приватная, в ней автор и бот; добавление людей — решение автора.
- [Тексты проходят через Cloudflare и хранятся в группе Telegram] → в политику (`public-launch-readiness`, Б2): что видит автор (имя, @username, id, язык, сообщения), что хранит D1 (перечень выше).
- [Права токена Cloudflare] → выкатка с привязкой D1 может потребовать права сверх `Workers Scripts: Edit`; проверяется первой выкаткой из CI до регистрации вебхука, сайт от сбоя job `worker` не зависит.

## Migration Plan

1. До мержа, владелец: супергруппа «Τετράδιο — поддержка», включены темы, @TetradioBot — администратор с «Управлением темами»; id группы (`-100…`) — из адреса группы в web.telegram.org.
2. До мержа, агент с авторизованным `wrangler`: `wrangler d1 create tetradio-feedback` → id в `wrangler.jsonc` (привязка `FEEDBACK`), `wrangler d1 migrations apply tetradio-feedback --remote`; `SUPPORT_CHAT_ID` и `SENTRY_EVENT_URL` — в `wrangler.jsonc`; записать текущую версию Worker (`wrangler deployments list`) для отката.
3. Мерж → job `worker` выкатывает новую версию; без `BOT_TOKEN` она работает в запасном режиме.
4. Агент: `wrangler secret put BOT_TOKEN` (из `.env.bot`), перерегистрация вебхука скриптом с `max_connections: 1`.
5. Проверка на устройстве (задача 3.3).

Откат: `wrangler rollback <версия bot-start>` — бот снова отвечает «пока не читаются»; `wrangler secret put` создаёт новые версии, поэтому откат — на записанный id, а не на «предыдущую». Темы и D1 остаются.

## Реализация

- Группа поддержки — «Τετράδιο — поддержка», `-1004455365743`, темы включены; 26.10.2026 у бота-администратора не было права «Управление темами» — включает владелец, проверка `getChatMember` перед регистрацией вебхука (задача 3.2.1).
- D1 `tetradio-feedback` (`a1f5ff25-9e0b-4e38-b007-b9cd3982112d`, регион WEUR) создан, миграция `0001_users.sql` применена 26.10.2026. Версия Worker до изменения для отката — `785bdb35-4093-43d5-b7c7-31381f301666`.
- `bot/worker.ts` — проверки запроса и сборка зависимостей; `respond` выбирает запасной режим (`legacyReply`) или `handle` из `bot/feedback.ts`. Ответ в теле — и для служебных сообщений в теме (`/block`, «Не доставлено»): им тоже не нужен токен.
- Разбор команды отрезает `@<бот>` и не различает регистр; `/start` с параметром распознаётся по второму слову.
- Сохранение после копии (`ack_at`, снятие `fb`) ждёт завершения (последовательная доставка), но его сбой игнорируется: доставленное сообщение не превращается в «Не удалось передать»; худшее последствие — ещё одно текстовое подтверждение.
- Ссылка на отчёт и копия повторяются вместе в новой теме, если старую удалили; без `SENTRY_EVENT_URL` в тему идёт голый id отчёта. Служебные сообщения в личном чате (обои, закреп, автоудаление и подобные) пропускаются до чтения хранилища — без темы и без ответа. Если шапка новой темы не отправилась, тема остаётся без шапки.
- В теме ошибка, не пришедшая от Telegram (исключение `fetch`), показывается как «Bot API недоступен», без текста исключения: в нём может быть адрес с токеном. Сбой хранилища при ответе автора — «Не доставлено: хранилище связей недоступно» в теме.
- Закрытая тема (`TOPIC_CLOSED`) не восстанавливается автоматически — проверка на устройстве (3.3).
- Стартовый граф `app/index.html`: 596 045 → 597 064 байт (+1 019) при той же сборке, предел 620 000.
- `tests/helpers/sqlite-d1.ts` — обёртка `node:sqlite` с интерфейсом D1 для запросов `bot/store.ts` той же миграцией.
- В e2e-сборке нет `VITE_TELEGRAM_BOT` и запуск — веб: кнопок обратной связи там нет по спеке; скриншоты сняты временным тестом со сборкой `VITE_TELEGRAM_BOT=TetradioBot` (390 px) и удалены.
- Нестабильный тест `tests/hidden-course-screens.test.tsx` («/words открывается без английского…») изредка падает под нагрузкой полного прогона и проходит отдельно — не связан с изменением.
