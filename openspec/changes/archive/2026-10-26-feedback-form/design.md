## Context

`bot-feedback` (PR #297, ещё не архивирован) принимает сообщения в чате бота и копирует их в тему пользователя в группе поддержки: `bot/feedback.ts` — `fromUser` (тема, шапка, ссылка на отчёт, копия, подтверждение), связи — D1 `tetradio-feedback`, таблица `users` (`bot/migrations/0001_users.sql`). Вебхук — `POST /` с заголовком секрета (`bot/worker.ts`). В приложении «Написать автору» вызывает `openFeedback` (`src/platform/feedback.ts`): `openTelegramLink` на `t.me/<бот>?start=…`. Mini App открыт на `https://tetradio.app/app/`, Worker — `https://tetradio-bot.lobanov-andrey-lavich.workers.dev`. В мосте Telegram есть `initData` (`src/platform/telegram-types.ts:51`); `requestWriteAccess` в типах нет. Экран сбоя входит в стартовый граф (`src/main.tsx:12`), бюджет — 620 000 байт, сейчас 597 064.

## Goals / Non-Goals

**Goals:**

- Отправка из приложения без сворачивания, с тем же результатом в группе, что и сообщение в чате.
- Отправитель — только тот, кого подписал Telegram: подделать имя и id нельзя.

**Non-Goals:**

- Вложения из формы, ответы автора внутри приложения.
- Проверка `initData` для других целей (синхронизация, профиль).

## Decisions

**Отдельный адрес `POST /feedback`.** Вебхук остаётся на `/` со своим секретом; форма — на `/feedback` без секрета вебхука, её подлинность — подпись `initData`. Альтернатива — одна точка с разбором по телу: смешало бы две модели доверия.

**Проверка `initData`.** По документации Mini Apps: `secret_key = HMAC_SHA256(key = "WebAppData", data = BOT_TOKEN)`, `hash = hex(HMAC_SHA256(key = secret_key, data = data_check_string))`, где `data_check_string` — все пары `key=value` после URL-декодирования, кроме `hash` (поле `signature` Bot API 8.0 входит), отсортированные по ключу, через `\n`; `user` — строка как пришла, без повторной сериализации. Проверка — `crypto.subtle.verify` (постоянное время). `auth_date` — не старше 7 суток и не в будущем больше чем на минуту: `location.reload()` (кнопка «Перезапустить») возвращает тот же `initData`, и суточный срок давал бы устаревший запуск у долго открытого приложения; повтор подписанных данных ограничен частотой и даёт только сообщение автору от того же пользователя. Пользователь — из поля `user` подписанных данных, не из тела запроса; без `user` — отказ.

**Тело и ответы.** Тело — не больше 16 КБ: `Content-Length` и затем побайтовый счёт при чтении потока (без `Content-Length` `request.text()` прочитал бы тело любого размера). `version` и `platform` не подписаны: только `[\w.+() -]`, до 32 символов, иначе `invalid`; текст считается после `trim`. Ответы: `200 {ok: true}`; `400 {error: "invalid"}` — нет текста, длиннее 3000 символов, тело не JSON, поля не того формата; `401 {error: "stale"}` — подпись не сошлась или `auth_date` старше 7 суток; `429 {error: "rate"}`; `502 {error: "failed"}` — сбой Bot API или D1. Без `BOT_TOKEN`, `SUPPORT_CHAT_ID` или D1 — `503 {error: "failed"}`: приложение показывает ошибку, как при сбое.

**CORS.** Запрос — `fetch` с телом JSON и `Content-Type: text/plain`: простой запрос без предварительного `OPTIONS`, на мобильной сети на один круг меньше. Разрешённые адреса страницы — переменная `APP_ORIGINS` (`https://tetradio.app`), сравнение точное; `Access-Control-Allow-Origin` и `Vary: Origin` — только для них, чужой `Origin` — `403` без них. `OPTIONS` всё же обрабатывается (`Allow-Methods: POST`, `Allow-Headers: Content-Type`, `Max-Age`) на случай клиента, который его пошлёт. Маршрут `/feedback` и `OPTIONS` разбираются до проверки метода и секрета вебхука (`worker.ts:49-50`). Проверка адреса не заменяет подпись: вне браузера заголовок подделывается, доверие — только подписи.

**Общий путь в тему.** Из `fromUser` выделяется доставка: строка пользователя → при необходимости тема и шапка → ссылка на отчёт → полезная нагрузка → повтор в новой теме при удалённой. Для чата нагрузка — `copyMessage`, для формы — `sendMessage` с текстом:

```
Из приложения · <версия> · <платформа>
ответить нельзя: бот не может писать пользователю   ← только при отказе в разрешении
<пустая строка>
<текст пользователя>
```

Без разметки (`parse_mode` не задаётся): текст пользователя не интерпретируется. 3000 символов текста плюс шапка (версия и платформа до 32 символов) меньше предела Telegram 4096. Служебное `write_access_allowed`, которое Telegram присылает в чат после разрешения, уже пропускается (`bot/feedback.ts`). Подтверждение в чат бота форма не шлёт: пользователь видит его в приложении. Ссылка на отчёт — из тела формы (`reportId`, 32 шестнадцатеричных символа), не из `fb` строки.

**Частота и записи без гонок.** Обработка формы не сериализована с вебхуком (`max_connections: 1` касается только вебхука), поэтому полная перезапись строки (`store.save`) могла бы затереть `/block`, `ack_at` или `fb`, записанные вебхуком в ту же секунду. Хранилище переходит на точечные записи: `INSERT OR IGNORE` строки пользователя, `setThread`, `setAck`, `setFb`, `setBlocked` — каждая меняет свои столбцы; вебхук пользуется ими же. Миграция `0002_form_at.sql`: столбец `form_at`. Слот формы занимается до доставки одним запросом `INSERT … ON CONFLICT (user_id) DO UPDATE SET form_at = excluded.form_at WHERE users.form_at IS NULL OR users.form_at <= ?`; ноль изменённых строк — `429`. Слот занимается и при сбое доставки: повтор раньше 10 секунд получает «Подождите несколько секунд», зато повтор после частичной доставки не дублирует сообщение. Двойное нажатие и повтор после обрыва не дают двух сообщений. Форма и сообщение в чате нового пользователя в одну секунду могут создать две темы — принимается; ответ потерян после доставки, и пользователь повторил через 10 секунд — сообщение придёт дважды, тоже принимается.

**Разрешение писать.** Если подписанный `user.allows_write_to_pm` истинен — вопроса нет. Иначе `WebApp.requestWriteAccess(callback)` при `isVersionAtLeast("6.9")`, в `try/catch` (`WebAppMethodUnsupported`, `WebAppWriteAccessRequested`) и с тайм-аутом 30 секунд — человек читает системный вопрос: метод в объекте есть всегда — мост грузится с telegram.org (`src/platform/bridge.ts`), а клиент может не ответить. Старый клиент, исключение или тайм-аут — `canReply: true` (неизвестно, считаем, что можно). Ответ запоминается до конца запуска: подписанные данные после него не обновляются, и без памяти вопрос повторялся бы перед каждым сообщением. Результат — `canReply` в теле; он не подписан, но подмена вредит только самому отправителю. «Отправить» недоступна с нажатия, включая показ вопроса. Отказ — сообщение уходит, в теме пометка, у пользователя текст про невозможность ответа.

**Форма в приложении.** `src/features/feedback/FeedbackForm.tsx` раскрывается на месте под кнопкой, без модального окна: так же работает на экране сбоя вне роутера и без базы. Компонент грузится динамическим импортом по нажатию — стартовый граф (экран сбоя в нём) не растёт. Если чанк не загрузился (старая страница после выкатки, нет сети), вместо формы — кнопка перехода в чат: ошибка из `lazy` иначе уронила бы экран сбоя, у которого нет границы ошибок выше, или вызвала бы экран сбоя в «Настройках». Пока чанк грузится — недоступная кнопка «Написать автору». Поле — `textarea` из `@/components/ui/textarea`, счётчик сверх предела, «Отправить», ссылка на скриншот (`openFeedback`, прежний переход). Черновик — в `localStorage` (`tetradio:feedback-draft`), стирается после успешной отправки: закрытие приложения при сбое или устаревшем запуске не теряет текст. Отправка — `sendFeedback` в `src/platform/feedback.ts`: `fetch(VITE_FEEDBACK_URL, …)` с `AbortController` на 15 секунд (доставка может ждать `retry_after` до 5 секунд), `initData` моста, `APP_VERSION`/`APP_BUILD`, платформой запуска и `reportId`. Тексты ошибок: сеть и прочее — «Не удалось отправить. Проверьте сеть и попробуйте ещё раз.»; `401` — «Закройте приложение и откройте снова — текст сохранится.»; `429` — «Подождите несколько секунд и отправьте снова.». Фокус в поле — по нажатию; на iOS клавиатура может не открыться программно — проверка на устройстве. Модуль `feedback.ts` без `sonner`.

**Когда формы нет.** Без `VITE_FEEDBACK_URL` (переменная репозитория, передаётся сборке в `env` шага `npm run build` в `deploy.yml`, тип — в `src/globals.d.ts`), вне Telegram (`launchContext().kind !== "telegram"`), в боте разработки (`launch.bot !== CONFIGURED_BOT`: его `initData` подписан другим токеном) или без моста с `initData` — кнопка ведёт себя как сейчас (`openFeedback`). Доступность проверяется в момент нажатия, а не при показе: экран отказа базы появляется раньше, чем загружается мост (`src/main.tsx`), и иначе остался бы старый переход. e2e-сборка без адреса формы остаётся на прежнем поведении.

## Risks / Trade-offs

- [`initData` в теле запроса к Worker] → строка уже подписана Telegram и не даёт доступа к аккаунту; в Worker не логируется; срок 7 суток.
- [Пользователь закрыл приложение во время отправки] → запрос может не дойти; черновик остаётся в `localStorage`.
- [Форма и чат одновременно] → вторая тема для нового пользователя; редкость.
- [`requestWriteAccess` на части клиентов показывает вопрос при каждом запуске] → вопрос — один раз за запуск, только перед отправкой.
- [Стартовый граф] → форма — отдельный чанк по нажатию; в стартовом графе только кнопка и проверка доступности; проверка `check:bundle`.
- [Что уходит автору] → поля подписанного `user` (имя, @username, id, язык), текст, версия, платформа, id отчёта; `initData` в D1 и журналах не хранится — в политику (`public-launch-readiness`, 1.2).

## Migration Plan

1. До мержа, агент: `wrangler d1 migrations apply tetradio-feedback --remote` (столбец `form_at`; старый код пишет строку явным списком столбцов и с ним совместим).
2. Мерж → выкатка Worker и сайта. Сайт собирается без `VITE_FEEDBACK_URL` — прежнее поведение.
3. Агент: job `worker` зелёный, `curl` на `/feedback` с `Origin: https://tetradio.app` отвечает `400 invalid` (маршрут есть); затем `gh variable set VITE_FEEDBACK_URL` и повторная выкатка сайта (`workflow_dispatch`). Обратный порядок дал бы форму без адреса у Worker — каждая отправка «Не удалось отправить».
4. Проверка на устройстве.

Откат: `gh variable delete VITE_FEEDBACK_URL` и повторная выкатка сайта — кнопки снова открывают чат; затем при необходимости `wrangler rollback` на версию после `bot-feedback` (из `wrangler deployments list`).

## Реализация

- Хранилище (`bot/store.ts`) перешло на точечные записи: `setThread`, `setAck`, `setFb`, `setBlocked`, `claimForm`; вебхук пользуется ими же. `claimForm` — `INSERT OR IGNORE` строки и условный `UPDATE … form_at`, результат — по числу изменённых строк (`meta.changes` в D1).
- Общий путь в тему — `intoTopic` в `bot/feedback.ts` (тема при необходимости, ссылка на отчёт, полезная нагрузка, повтор в новой теме); чат кладёт `copyMessage`, форма — `sendMessage` с `formText` (`bot/texts.ts`).
- `bot/form.ts`: `readForm` (тело до 16 КБ, поля по формату), `verifyInitData` (`crypto.subtle.verify`, сортировка ключей по кодовым точкам, 7 суток, не больше минуты из будущего). Маршрут — `feedbackForm` в `bot/worker.ts`, до проверки метода и секрета вебхука; исключение — `502` без CORS, приложение показывает «Не удалось отправить».
- `ImportMetaEnv` в проекте не типизирован отдельно (переменные Vite — через тип `vite/client`), поэтому `src/globals.d.ts` не менялся. Адрес формы читается при каждом вызове (`feedbackUrl()`), а не при загрузке модуля.
- Приложение: `src/platform/feedback.ts` — `formAvailable` (в стартовом графе); `src/platform/feedback-send.ts` — `askWriteAccess` и `sendFeedback`, грузятся вместе с формой; `src/features/feedback/FeedbackButton.tsx` — кнопка с проверкой доступности при нажатии и `React.lazy` формы; `FeedbackForm.tsx` — форма.
- Стартовый граф `app/index.html`: 597 064 → 598 132 байт (+1 068) при сборке с `VITE_TELEGRAM_BOT` и `VITE_FEEDBACK_URL`.
- Миграция `0002_form_at.sql` применена к `tetradio-feedback` 26.10.2026.
- После ревью кода: отказ загрузки чанка — переход в чат (`tests/feedback-chunk.test.tsx` падал без исправления: экран сбоя сменялся границей ошибок); кнопка экрана сбоя снова `xl`/`outline` как соседние; ответ на вопрос о разрешении запоминается, тайм-аут 30 секунд; фокус возвращается в поле после ошибки, текст ошибки — `--pen`, ссылка на скриншот — `primary` и не ниже 44 px; счётчик «Длиннее на N — предел 3000 символов.»; тело читается с ограничением без `Content-Length`; слот формы — одним запросом; тест неверной подписи больше не зависит от случайного первого символа хеша.
- Скриншоты формы и состояния «Отправлено» сняты временным e2e на эмуляторе Telegram (`tests/e2e/telegram.ts`, `initData` подставлен) со сборкой `VITE_TELEGRAM_BOT`/`VITE_FEEDBACK_URL`, 390 px; тест удалён. Плавающее меню перекрывает низ формы до прокрутки; поведение с клавиатурой — на устройстве (3.3).
- 26.10.2026 после мержа: job `worker` зелёный; `/feedback` с `Origin: https://tetradio.app` — `400 invalid` с CORS, с чужого адреса — `403`; `VITE_FEEDBACK_URL` задана, сайт пересобран (`workflow_dispatch`), адрес — в чанке `feedback-*.js` опубликованной сборки. Владелец проверил на iPhone: форма из «Настроек» раскрывается без сворачивания приложения, сообщение приходит в тему, ответ — в чат бота. Экран сбоя, отказ в разрешении, закрытая тема, ссылка на событие Sentry и Desktop на устройстве не проверялись — отдельная строка таблицы `docs/telegram.md`. Перечень данных формы для политики перенесён в задачу 1.2 `public-launch-readiness`.
